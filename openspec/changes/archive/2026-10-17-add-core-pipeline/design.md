# Design

## Context

Что уже есть:
- **Шлюз** (`gateway/`, ADR 0002): Receiver выдаёт по каждому участнику из whitelist события `segmentStart` / `frame` / `segmentEnd`. Кадр — 20 мс, PCM s16 моно 48 кГц, время — `Date.now()`. Discord-клиенты не шлют пакеты в тишине, поэтому `frame` приходят только во время речи, а поток подписки закрывается сам через 1 с без пакетов. Player пишет PCM в `PassThrough` и умеет `stop()` немедленно. Recorder пишет WAV в `data/recordings/<Сессия>/`.
- **Политика Диалога** (`terebot.dialogue`): чистая синхронная логика. На входе `Utterance`, `SpeechActivity`, `CloneStarted`, `ClonePhraseEnded`, `CloneFinished`, `ResponseFailed`, `ParticipantLeft`, а также `tick(now)`. На выходе решения `Respond`, `AddToContext`, `InterruptClone`, `StopAfterCurrentPhrase`, `CancelPendingResponse` и другие, каждое с `reason`. Время — секунды в одной шкале.
- **Голос** (этап 3): Qwen3-TTS 1.7B MLX 8-bit, `mlx-audio` 0.5.9, стриминг `streaming_interval=0.5`, `mx.set_cache_limit(1 ГБ)`, прогрев со стримингом. С LLM рядом: пик 4,44 ГБ, swap не растёт, первый звук 0,59 с, RTF 0,72. Выход — 24 кГц.
- **LLM**: `llama-server` (llama.cpp 0.6.0, Homebrew) с `unsloth/Qwen3.5-4B-GGUF` Q4_K_M, `-c 4096`, RSS ~3 ГБ. Рассуждения выключаются флагом `--reasoning off` (проверено по `llama-server --help` 2026-10-17).
- **Распознавание**: `gigaam-v3-e2e-ctc` через `onnx-asr` 0.12.0, только с `CPUExecutionProvider` (на CoreML падает).
- **Smart Turn v3.2**: `pipecat-ai/smart-turn-v3`, файл `smart-turn-v3.2-cpu.onnx` (ревизия `f766f81`), BSD-2, русский поддерживается. Вход — последние ≤ 8 с моно 16 кГц через `WhisperFeatureExtractor(chunk_length=8)`, вход `input_features`, выход — вероятность завершённости, порог 0,5 (`inference.py` upstream).
- **Настройки**: общий TOML (`runtime-config`); секции разбирают и шлюз, и ядро, а неизвестные секции оба пропускают.

## Goals / Non-Goals

**Goals:**
- Полный цикл «Реплика → ответ голосом» в Discord на одном M1 Pro, в бюджете памяти этапа 3.
- Политика Диалога остаётся единственным местом, где решается, кому и когда отвечать. Ядро только переводит звук в её события и исполняет её решения.
- Каждый этап цикла замеряется, чтобы этап 7 проверял порог ≤ 4 с по Журналу.

**Non-Goals:**
- Pipecat и другие фреймворки голосовых агентов. Транспорт, Политика и шлюз у нас свои, а фреймворк навязал бы свою модель событий поверх них. Smart Turn берём как отдельную ONNX-модель.
- Подбор порогов под задержку ≤ 4 с: это этап 7, здесь только разумные значения по умолчанию в настройках.
- Обработка нескольких одновременных ответов: Клон в каждый момент готовит или произносит не больше одного.

## Decisions

### Процессы и запуск
Три процесса на Mac:
- **шлюз** — `cd gateway && npm start`, как раньше;
- **ядро** — `uv run --group core python -m terebot.core`;
- **`llama-server`** — его запускает ядро как дочерний процесс с параметрами из `[llm]`, если на заданном порту ещё никто не отвечает, и останавливает при выходе.

Порядок запуска шлюза и ядра любой.

Голос живёт в процессе ядра: память Голоса и LLM уже замерена именно в такой раскладке (бенчмарк — один процесс плюс `llama-server`). Отдельный процесс для Голоса добавил бы ещё один протокол без выигрыша в памяти.

Новая группа uv `core`: `mlx-audio==0.5.9` (тянет `transformers>=5.14`, `mlx`), `onnx-asr[cpu,hub]==0.12.0`, `websockets`, `psutil`, `num2words`, `soundfile`. Конфликтует с `tts-qwen-torch`, `tts-chatterbox` и `train`. Torch в ядре не нужен: Silero VAD берём в ONNX.

### Протокол шлюз ↔ ядро
Ядро — WebSocket-сервер на `127.0.0.1:<[core].port>`, шлюз — клиент: встроенный `WebSocket` Node 22, без новых npm-пакетов. Шлюз переподключается каждые 3 с. После подключения он присылает `hello` с текущим состоянием: есть ли Сессия, её каталог, участники в канале. Так перезапуск ядра не требует повторного `/join`. После `session_start` шлюз присылает `participant_joined` и для тех, кто уже сидел в канале до `/join`: иначе ядро не знало бы их имён.

Сообщения двух видов:
- **Управляющие** — JSON-тексты `{"type": ..., ...}`:
  - шлюз → ядро: `hello`, `session_start {session, t}`, `session_end`, `participant_joined {user_id, name, t}`, `participant_left {user_id, t}`, `segment_start` / `segment_end {user_id, t}`, `playback_started` / `phrase_ended {response_id, phrase, t}`, `playback_finished {response_id, t, interrupted}`;
  - ядро → шлюз: `phrase_begin {response_id, phrase}`, `phrase_end_marker {response_id, phrase}`, `response_end {response_id}`, `stop_after_phrase {response_id}`, `stop_now`. `response_end` — фраз в ответе больше не будет: без него шлюз не отличит конец ответа от фразы, которую LLM ещё генерирует.
- **Бинарные** — звук. Заголовок 16 байт: тип (1 байт: 1 — звук участника, 2 — звук ответа), 7 байт резерва, `t` в мс (float64 LE). Для звука участника дальше идёт user ID (uint64 LE), для звука ответа — `response_id` и номер фразы (uint32 LE каждый). Затем PCM s16le моно 48 кГц. Звук ответа ядро ресемплирует 24 → 48 кГц само (`resample_poly` ×2), чтобы шлюзу осталось только `monoToStereo`.

Кодек сообщений — чистая логика с двух сторон: `gateway/src/core-protocol.ts` и `terebot.core.protocol`. Тесты с обеих сторон сверяют один и тот же байтовый пример (`tests/fixtures/core-protocol/`). Звук участников не из whitelist шлюз не шлёт: Receiver и так подписывается только на них.

Время — `Date.now()` шлюза в мс. Ядро на той же машине переводит его в секунды Сессии (`(t − t_session_start) / 1000`) для Политики. Свои события, например сбой ответа, ядро ставит по `time.time()` в той же шкале.

### Очередь фраз в шлюзе
Новый модуль `speech-out.ts`. Ядро шлёт звук фразы кусками по мере синтеза, а шлюз складывает их в очередь `(response_id, фраза) → кадры`. Таймер раз в 20 мс подаёт в Player по одному кадру, как это уже делает режим эха. Поэтому шлюз точно знает, какая фраза звучит:
- первый кадр ответа → `playback_started`;
- последний кадр фразы после `phrase_end_marker` → `phrase_ended`;
- `phrase_ended` последней фразы после `response_end` → `playback_finished`;
- если звук фразы ещё не пришёл, таймер ждёт, а не объявляет фразу законченной.

`stop_after_phrase` выбрасывает очередь за текущей фразой, `stop_now` вызывает `Player.stop()` и очищает очередь. Логика очереди без таймера и Discord — чистая, её проверяет `node:test`.

### Восприятие речи (`speech-input`)
Для каждого участника — свой `Listener`.
1. **Звук** — кадры 48 кГц прореживаются до 16 кГц (`resample_poly` 1/3) в кольцевой буфер Реплики.
2. **VAD** — Silero VAD в ONNX (`src/silero_vad/data/silero_vad.onnx` из snakers4/silero-vad, тег `v6.2.3` — та же версия, что в группе `data`), окна по 512 сэмплов 16 кГц, состояние модели — своё у каждого участника. Вероятность > `[speech].vad_threshold` (0,5) — речь.
3. **Активность** — пока идёт речь, раз в 100 мс отправляется `SpeechActivity(user_id, duration_ms)`. Длительность непрерывной речи не сбрасывается паузами короче `[speech].continuity_ms` (300 мс).
4. **Кандидат в конец хода** — тишина по VAD дольше `[speech].silence_ms` (200 мс), или кадры перестали приходить на столько же: Discord-клиент не шлёт тишину. Тогда Smart Turn получает последние 8 с Реплики. Вероятность > 0,5 → Реплика закончена. Иначе ждём новой речи, но не дольше `[speech].max_pause_ms` (1500 мс) с момента конца речи: после этого Реплика закончена принудительно.
5. **Распознавание** — GigaAM e2e-ctc по всей Реплике в пуле потоков. Реплика длиннее `[speech].asr_max_s` (20 с) делится по паузам VAD и распознаётся частями. Пустой текст → Реплика отбрасывается. `Utterance.t_end` — конец речи по VAD, а не момент готовности текста.

Решение «закончена ли Реплика» — чистый конечный автомат: на входе события «кадр / вероятность VAD / результат Smart Turn / время», на выходе действия. Его проверяют юнит-тесты на синтетических последовательностях. VAD, Smart Turn и GigaAM — обёртки, их проверяет запуск на записях пробной Сессии.

### Цикл ядра
Один asyncio-цикл. Модели работают в потоках:
- распознавание и Smart Turn — в `ThreadPoolExecutor`;
- Голос — в одном выделенном потоке: MLX держит состояние на поток, и так синтез не идёт параллельно.

Каждое событие проходит путь `Политика.handle(event)` → решения → исполнитель. Таймер в 100 мс вызывает `Политика.tick(now)`.

Исполнитель решений:
- `Respond` — запустить задачу ответа (если идёт старая, её уже отменило предыдущее решение Политики);
- `CancelPendingResponse` — отменить задачу: закрыть HTTP-поток LLM и сбросить синтез;
- `InterruptClone` — `stop_now` в шлюз и отмена задачи;
- `StopAfterCurrentPhrase` — `stop_after_phrase` в шлюз, остановка генерации новых фраз;
- `AddToContext` — Реплика в историю Сессии;
- остальные — только запись в Журнал.

`playback_started`, `phrase_ended` и `playback_finished` от шлюза превращаются в `CloneStarted`, `ClonePhraseEnded` и `CloneFinished`.

### Ответ Клона (`clone-response`)
**Промпт.** System — Паспорт (`config/passport.md`) целиком и короткие правила устной речи: отвечать кратко, одной–тремя фразами, без разметки, эмодзи и списков, числа словами, говорить от лица Прототипа. Дальше — few-shot из `config/fewshot.jsonl` как пары user/assistant. Затем история Сессии:
- Реплики из контекста — сообщения `user` вида «Вася: …»;
- ответы Клона — `assistant` в прозвучавшей части с пометкой «(перебили)», если ответ оборвали;
- Реплики, на которые нужно ответить, — последнее `user`-сообщение.

Бюджет — `[llm].context_tokens` (3 000 из `-c 4096`, остальное — на ответ). Токены считает `/tokenize` `llama-server`, старые Реплики отбрасываются первыми. Сборка промпта и обрезка — чистая логика с юнит-тестами, подсчёт токенов в них подменяется.

**LLM.** `POST /v1/chat/completions` с `stream: true`, `max_tokens` из настроек; `llama-server` запускается с `--reasoning off`. На случай, если блок `<think>…</think>` всё равно пришёл, он вырезается до деления на фразы.

**Фразы.** Потоковый делитель режет текст по `.`, `!`, `?`, `…` и переводу строки, но не раньше `[voice].min_phrase_chars` (20 символов), чтобы не синтезировать «Ну.» отдельно. Исключение — последняя фраза ответа: склеить её с предыдущей нельзя, та уже ушла в синтез. Длинную фразу без точки он режет по запятой после `[voice].max_phrase_chars` (200). Это чистая логика.

**Текст для Голоса** — чистая функция:
- убрать эмодзи и разметку;
- применить `config/lexicon.tsv` (слово → запись для Голоса, по границам слов, без учёта регистра);
- оставшиеся числа превратить в слова `num2words(lang="ru")`.

Склонять числа `num2words` не умеет («в 2026 году» → «в две тысячи двадцать шесть году»), поэтому главная защита — правило в промпте писать числа словами, а `num2words` — страховка. В Журнал пишутся оба текста.

**Голос.** `[voice]` задаёт либо `model` + `ref_audio` + `ref_text` (zero-shot Base, как на этапе 3), либо `model` + `speaker` (дообученная модель этапа 5). Адаптер повторяет найденное в `bench_voice.py`: `mx.set_cache_limit`, прогрев со стримингом при запуске, `generate(..., stream=True, streaming_interval=0.5)`. Код адаптера не копируется из скрипта бенчмарка, а выносится в `terebot.voice`, и бенчмарк переходит на него. Тогда Клон и бенчмарк гарантированно синтезируют одинаково.

Фразы синтезируются по очереди. Следующая фраза начинает синтезироваться, когда закончился синтез предыдущей, а не её звучание. Так очередь в шлюзе не пустеет между фразами.

**Приветствие.** На `session_start` ядро берёт случайную строку из `[voice].greetings` и отправляет её как ответ с `response_id` вне Диалога. Политике события речи Клона для приветствия не передаются: Диалога нет, и перебивать нечего.

**Сбой.** Ошибка или таймаут LLM (`[llm].timeout_s`) или исключение Голоса → `ResponseFailed`, запись в Журнал, звук не идёт.

### Журнал Сессии (`session-journal`)
`data/sessions/<Сессия>/journal.jsonl` — по строке JSON на событие, с `flush` после каждой. Имя каталога приходит от шлюза в `session_start` и совпадает с каталогом записей.

Типы строк:
- `utterance`, `decision` (с `PolicyState`), `response`, `error` — при `[journal].transcripts = true`;
- `latency`, `memory`, `summary` — при `[journal].metrics = true`.

Когда транскрипты выключены, у `decision` и `response` вместо текста пишется только длина.

**Задержка.** Метки времени ставятся в одной шкале:
- `t_end` Реплики;
- решение о конце хода;
- готовый текст;
- запрос в LLM;
- первый токен;
- первая фраза;
- первый чанк Голоса;
- `playback_started` из шлюза.

Сводка Сессии — медиана и p90 «`t_end` → `playback_started`».

**Память.** Сэмплер раз в секунду пишет RSS ядра, `mlx` active + cache, RSS `llama-server` (по PID дочернего процесса), занятую память системы и swap (`psutil`). Это тот же способ, что в бенчмарке этапа 3, чтобы цифры были сравнимы.

### Настройки
Новые секции в `config/settings.toml` со значениями по умолчанию:
- `[core]` — `port`;
- `[speech]` — пороги VAD, тишины и паузы, предел распознавания;
- `[llm]` — путь к GGUF, `port`, `context_tokens`, `max_tokens`, `timeout_s`;
- `[voice]` — модель, референс или говорящий, интервал стриминга, лимит кэша, длины фраз, приветствия;
- `[journal]` — `transcripts`, `metrics`.

Шлюз читает только `[core].port`. Как и прежде, ядро проверяет при старте все секции и падает с понятной ошибкой.

Файлы личности появляются как шаблоны:
- `config/passport.md` — разделы из PLAN, текст-заглушка «заполнить на этапе 7»;
- `config/fewshot.jsonl` — 2–3 примера-заглушки;
- `config/lexicon.tsv` — пример `cs → кс`.

Реальные Паспорт и few-shot содержат личные данные Прототипа, поэтому рядом лежат `*.local.*` в `.gitignore` — по образцу `settings.local.toml`. Если локальный файл есть, читается он.

## Risks / Trade-offs

- [Smart Turn обучен не на Discord-звуке после Opus, на нём хуже отличает паузу от конца] → предельная пауза ограничивает ожидание сверху, пороги вынесены в настройки, проверка на записях пробной Сессии — отдельная задача.
- [Discord не шлёт тишину, и VAD не видит её внутри потока] → конец речи определяется и по VAD, и по отсутствию кадров; оба порога одинаковые.
- [Распознавание, Smart Turn и Голос делят CPU и GPU, и при одновременной речи двух участников ответ задерживается] → распознавание только законченных Реплик и пул из 2 потоков; замер в Журнале покажет, нужно ли больше.
- [GigaAM на CPU для длинной Реплики занимает секунды] → это попадает в задержку «готовый текст» и видно в Журнале; для этапа 7 есть запас — CTC-вариант уже самый быстрый.
- [Память: ядро добавляет к замеру этапа 3 GigaAM (~1 ГБ по плану), VAD и Smart Turn (десятки МБ)] → проверка памяти всей системы с LLM без роста swap — в задачах; если не уложимся, первый кандидат — меньший `-c` LLM или конфигурация 4 этапа 3.
- [`num2words` не склоняет числа] → правило в промпте, а склонение — после MVP, если в Журнале будет много ошибок.
- [Ответ LLM в стиле ассистента («Конечно! Вот…»), пока Паспорт — заглушка] → для этапа 6 это допустимо, манера — этап 7.
- [Протокол в двух языках разъедется] → общий байтовый пример в фикстурах, тесты с обеих сторон.
- [Время шлюза и ядра на одной машине, но `Date.now()` может прыгнуть при синхронизации часов] → внутри Сессии используется разность с её началом; скачок часов посреди Сессии считаем редким и не обрабатываем.

## Open Questions

- Конкретные пороги `[speech]` (200 / 300 / 1500 мс) — уточняются на записях пробной Сессии и в живом прогоне; на спеки и задачи не влияют.
